# Meari 实时摄像头

从 `0.2.6b4` 起，选中的 ORVIBO 摄像机/录像机可以通过厂商云授权、XTS P2P/中继链路
接入 HA 的 `camera` 实体。仅限实际返回 iotType=3、p2p=2 的 IPC(devTypeID=2) 或
NVR(devTypeID=11)，默认 hostKey 鉴权；其他 SDK、独立视频密码和声音未接入。

## 使用

1. HACS 更新到 `v2.0.0b1` 或后续适用版本，重启 HA，并强制刷新浏览器。
2. 在集成设备选择中勾选录像机/摄像机，然后打开其设备页面。已实现的 Meari 路由显示
   “支持实时视频”；其他 SDK 显示“仅支持状态信息，视频暂未支持”。这不代表设备当前在线或连接已成功。
3. 打开新增的“通道 1”“通道 3”或“实时画面”摄像头实体。诊断传感器不显示画面。

仪表盘可使用 HA 自带的图片概览卡片（替换示例实体）：

```yaml
type: picture-glance
title: 录像机
camera_image: camera.your_nvr_channel_1
camera_view: live
entities: []
```

首次授权、P2P 协商和首帧需要数十秒。缩略图请求本身有较短超时；已建立的预连接
供下一次打开复用，未被播放请求使用的连接会自动释放。`2.0.0b5` 及更早版本只在平台
加载时发现通道，漏发现或插拔改变清单后可重新加载集成。`2.0.0b6` 增加自动补发现，
见下文；纯 LAN 模式无法提供必要的厂商授权。

## 通道恢复（2.0.0b6）

若某通道实体为 `unavailable`，属性仅有 `restored: true`，说明 HA 保留了历史实体，
当前平台没有创建对应的摄像机对象；这与已创建实体的 P2P/视频连接失败不同。
本轮真机排查确认露台通道 3 在云端已在线、支持 `p2p=2`，但 HA 仍为历史实体。
重载集成后实时和回放实体恢复为 `idle`，单路正常出画，640×360、H.264、请求码流
`100`，播放器时间从 180 秒推进至 344 秒。首次发现时遗漏的具体暂态条件未确定。

`2.0.0b6` 每 60 秒查询一次选中且支持视频的设备清单，沿用 UID 精确匹配、真实在线
通道与协议能力校验，自动补上恢复的实时/回放实体。稳定实体标识去重，空清单和
云端错误不删除已有实体；不重叠查询，卸载会取消查询并拒绝迟到结果。发现只获取
元数据，不启动 P2P 或 FFmpeg。已有实体的每次开流仍重新获取授权和实际通道。

新增离线回归涵盖恢复、去重、空清单、失败重试、设备选择、UID 变化、重叠和卸载。
全量 872 项测试通过、无跳过，包含真实 FFmpeg/PyAV。真机排查时用户 HA 为 `2.0.0b5`，
自动发现与共享读取修复尚未安装；本次露台播放后仍出现 `source_busy` 和源错误记录，
仍需更新后的真机验证，不能将单次重载恢复视为全部加载问题已解决。

HAOS 自带 FFmpeg；本集成声明 `ffmpeg` 与 `stream` 依赖，不需要额外的视频服务。
每个正在播放的通道使用一个协议子进程和一个 FFmpeg 进程；HEVC 软件转码会占用 CPU。
`2.0.0b4` 将协议进程的视频帧边界扫描改为底层字节查找，减少多路视频的解析开销，
保持原有视频输出字节、分辨率和帧率。FFmpeg 转码仍会消耗 CPU；本地解析性能对照
不代表 HA 整机的占用降幅。升级后请结合实际 CPU 曲线和页面连接情况判断改善程度。

## 源画质选择（2.0.0b5）

集成的“配置 → 摄像机实时画质”增加可选的“流畅”档。默认仍请求原来的码流编号 0；
流畅档只在当前设备或 NVR 当前通道明确上报标清能力时请求该档，画面细节可能减少。
保存选项会重载集成，重新打开实时画面后生效；该选项适用于本配置项的全部实时预览，
录像回放继续使用独立的原有请求。

- `bps2` 上报 profile `0` 时请求码流 `100`，对应 HomeMate 的标清档。
- 旧 `bps` 位图只选择已上报的标清编号，按 `2`（240P）、`1`（360P）、`3`（480P）优先。
- `vst=1`、没有标清档或能力缺失时保留编号 `0`；不猜测其他编号、不自动轮询不同档位。
- camera-tags、实际 NVR 通道、鉴权与录像命令不因画质设置改变。

`video_diagnostics.requested_quality` 显示 `default` / `fluent`，
`requested_stream_id` 在收到首个可输出关键帧后显示实际请求的编号。编号 `0` 表示保留
默认请求；该字段记录发送的请求，不能证明固件已按该档返回画面。实际编码仍以
`source_codec` 为准，流畅档不保证改为 H.264，软件转码仍会运行。

静态依据来自 HomeMate `5.2.6.307`（APK SHA256 与 [首帧协议](meari-video-probe.md) 相同）：
`com/orvibo/homemate/device/meari/video/z.java:22–52,70–86` 根据 `vst`、`bps2` 或 `bps`
生成可选画质；`res/values/arrays.xml:377–430` 对应标清 profile 0 → 100，以及旧编号
1/2/3 → 360P/240P/480P；`com/meari/sdk/utils/SdkUtils.java:777–813` 也将现代 profile
映射为 `100 + profile`。VVP 请求的 `0x38` 为画质编号，`0x39` 为 camera-tags，见首帧协议。
这里复用已有 JADX/Apktool 导出做离线核对，没有执行 APK，也没有联网操作真实摄像机。

用户确认 `2.0.0b4`、2 vCPU / 4 GiB 虚拟机中，单路播放时 HAOS 总 CPU 持续约 38%–43%，
内存约 1.3/4 GiB。截图没有逐进程 CPU 数据，不能单独量化 FFmpeg 与协议进程各自占比。
流畅档的实际分辨率、CPU 降幅和首次加载稳定性均需真机验证；不提升 `hardware_verified`。
增加到 4 vCPU 可为 HA 提供更多运行余量，但不等于视频计算量减半，也不会自动启用核显。
离线全量 856 项测试通过、无跳过，包含原有真实 FFmpeg 转码与 PyAV 解码，以及新增的
配置、标清能力门控、VVP 请求字节、私有参数传递和诊断过滤回归。

## 媒体与生命周期

- 平台按 App 的 Device.uid == CameraInfo.deviceID 匹配选中的设备，按真实通道编号
  建立实体。每次开流重新获取会话、库存和通道；库存排序变化不会切到另一台设备。
- 协议子进程通过 stdin 收取私有会话，通过有长度限制的 J/V 管道输出固定状态和
  Annex-B 视频。视频只在收到参数集和关键帧后输出；原先的首帧诊断模式继续保留。
- FFmpeg 从管道解码 HEVC/H.264，以 H.264/yuv420p 输出 MPEG-TS。HA Stream 从随机
  localhost 地址读取，再生成前端 HLS；go2rtc 也可读取此源供 WebRTC 使用。
  浏览器不直接连接私有厂商协议。
- 仅绑定 `127.0.0.1`，禁用访问日志。云账号、hostKey 不出现在 URL、命令行、诊断
  返回或视频文件中。不会自动存储视频；HA 用户主动调用录像功能属于独立操作。
- 同一实体共用 HA Stream，缩略图也复用其解码关键帧。`2.0.0b6` 的共享读取修复允许
  HA Stream 与 go2rtc 共用一套协议和转码进程，最多 4 个本地源读者；HA Stream 和
  go2rtc 各自仍可向多个前端分发。每个源读者的队列最多 1 MiB，积压或写入超过
  10 秒的读者单独断开；最后一个源读者退出、无媒体、超时、平台移除或 HA 关闭时
  回收协议和转码进程，包括进程生成期间取消的情况。录像回放不共享活动读取。
- 未使用的预连接20秒后回收；首个转码输出最多等待55秒，连续媒体无输出30秒退出，
  每个连接最多运行1小时，之后由 HA 正常重连。HA HLS 自身会保留短暂缓冲，关闭
  前端后释放不一定立即发生；开启 HA“预加载”会按该设置持续保持流。
- 首次打开和后续重试共用有时限的连接准备；HA 读取请求先超时或取消时，不会反复
  丢弃尚未完成的首次 P2P 连接。无人使用的准备结果仍会过期回收。首次预连接失败
  与播放中断均可触发有限恢复，最多重试3次，总预算120秒。
- 所有旧读者已断开、清理尚未完成时，新的本地读取最多等待 10 秒；仍有读者播放时，
  新的实时读取加入共享源，不替换原读者。

`video_stage` 是固定连接阶段，`streaming` 仅表示转码器已输出数据。静态 SDK 诊断
不能判断每台设备是否通过动态校验；实体是否生成以实际库存、身份匹配和通道能力为准。

## 频繁出现 Media unavailable

请同时保留实时实体的 `video_diagnostics` 和 HA `stream` 日志。`streaming` 只表示
视频桥输出了数据，即使 `last_frame_age_seconds: 0`，也不能证明 HA 已完成解复用或
浏览器已播放。`connection_attempts` 包含正常重新打开及未使用预连接的重新建立，
因此 `reconnect_count` 不能直接当作故障次数。

本地 `http://127.0.0.1:...` 地址出现 5XX，表示 HA 读取视频桥时被拒绝或源未准备好；
读取时的 `I/O error` 还需要结合超时和断开阶段判断，不能仅据此判断摄像机离线。
诊断中的 `last_error_stage` / `last_error_reason` 保留最近一次历史错误，恢复后不会清空。

`2.0.0b3` 新增 `http_503_count` 和 `last_http_error_reason`：`source_busy` 表示前一个
读取尚未释放，`source_unavailable` 表示源建立失败，`bridge_closed` 表示桥已关闭，
`playback_selection_required` 表示需要重新选择录像。只输出固定原因，不包含私有地址
或凭据。这些离线修复仍需在用户 HA 中确认首次打开及连续播放是否稳定。

`2.0.0b6` 的共享读取修复不再因已有正常实时读者而返回 `source_busy`，该原因仍用于
独占的录像回放。`reader_limit` 表示本地实时源读者已达上限；`active_readers` 是当前
实时源读者数量，`slow_reader_count` 记录因队列积压或写入超时退出的读者数量。
前端连接断开不计为摄像机源失败，源错误仍由 `failure_count` / `timeout_count` 记录。

## 验证边界

用户已确认真实 NVR 1 号通道可以观看；3号通道加载慢，稍后可观看。曾收到
153,474字节 HEVC 关键帧和参数集；现有用户验证确认实时播放。硬盘录像结果尚未收到。

2026-10-29 在用户 `2.0.0b5`、4 vCPU 的 HA 中将画质从默认切为流畅，通道 1 实际
返回码流 100、H.264、640×360，原生 WebRTC 播放器持续推进超过 5 分钟，但期间仍有
源错误与 HA Stream 的 `source_busy / 503`。通道 3 后续确认云端在线但 HA 未创建活动
实体，重载后恢复，详见上文“通道恢复”。本轮没有采集 CPU 曲线，不量化负载降幅。

共享读取修改前已在离线双读者测试中复现一个 200、一个 503，修改后两个读者均可
读取且仅启动一套进程。Python 3.12 全量 865 项测试通过，无跳过；真实 FFmpeg/PyAV
覆盖已有读者与晚加入读者连续解码。该修复尚未安装到用户 HA，不能据离线测试
宣布实际卡片加载和静帧问题全部解决。

`2.0.0b6` 发版前全量 887 项测试通过、无跳过（34.599 秒），包含上述真实媒体验证。
此前源故障恢复测试曾在首帧后 0.1 秒注入故障时首次响应为 503，单独复核和再次全量
均通过，保留该时序波动记录。本版修复仍需升级后验证。

本地测试包含真实 FFmpeg 合成 HEVC → H.264 MPEG-TS → 强制 H.264 解码，并覆盖
身份匹配、通道选择、会话刷新、进程超时、断开和取消清理。这些离线结果不能替代
真实画面和浏览器播放验证。当前无音频；帧时间按接收时钟建立，尚未移植设备音视频
时间戳及同步。网络抖动下的时序精度仍需实际验证。

硬盘历史使用另一组查询/回放指令，不能用实时关键帧结果确认。日历、片段、回放入口
已加入 `0.2.6b5`，尚待真实设备验证；操作见 [硬盘录像说明](meari-hdd-playback.md)。

`2.0` 分支继承上述视频能力，本次新增的是调光与 RF 窗帘协议，不构成新的视频实机
验证。本次发布范围见 [协议重构](protocol-profiles-2.0.md)，其他指南见 [文档索引](README.md)。
